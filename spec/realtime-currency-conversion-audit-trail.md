**Title:** Real-Time Currency Conversion & Audit Trail

**Business Idea:** Treasury operations teams at our enterprise customers currently convert currency using manual lookups against a third-party portal — slow, and it leaves no record for compliance. We need instant, self-serve conversion inside our own app, and because these are regulated transactions, every conversion must be reconstructable for an auditor on demand, not pieced together afterward from emails or spreadsheets.

**Persona:** Treasury operations analysts at enterprise customers, who process multiple cross-border settlements a day and are personally accountable if a conversion can't be justified during an audit.

**User Need:** See a trustworthy converted amount the moment I enter it — and be able to pull up any past conversion, with its rate and timestamp, the moment an auditor asks for it.

**Known Constraints:**
- Frontend must read `VITE_API_URL` dynamically at container runtime using
  a generic entrypoint script placeholder replacement; replace the placeholder token
  `__VITE_API_URL__` inside the built `index.html` (or equivalent) with the runtime
  `VITE_API_URL` value.
- Backend must read database configurations exclusively from runtime
  environment variables.
- Backend must query external currency conversion data exclusively using a base URL from an environment variable (`CURRENCY_API_BASE_URL`), defaulting to an unauthenticated open-source endpoint like Frankfurter (`https://frankfurter.dev`).
- The application must not hardcode third-party API response schemas; utilize flexible JSON property mapping or an abstraction layer to isolate internal compliance tracking from external JSON structure changes (such as `rates` vs `conversion_rates`).
- The audit trail record must capture the exact execution timestamp generated by your backend server alongside any date or sequence markers returned by the external provider, ensuring complete sub-second audit reconstruction even if the provider only exposes a calendar date.
- External HTTP calls must handle failures gracefully with fallback values or clear domain exceptions rather than bubbling up raw network or serialization errors.
- CI/CD pipeline must inject placeholders safely at deployment time without
  exposing sensitive data in container layers.
- Restricted to specific stack versions: React (Vite/Node 24.*) and C#
  (**backend must target `net10.0` for build/test; CI must use `dotnet-version: 10.0.x`**).
- Must adhere to a strict folder layout (`src/frontend` and `src/backend`).
- A .NET solution file must always be generated at `src/backend/OuterloopLabApi.sln` via `dotnet new sln` + `dotnet sln add`, with the backend project added to it, and CI/build/test commands must invoke this `.sln` rather than the `.csproj` directly.
- Deploy as a single Azure Container App using the sidecar pattern to host
  both frontend and backend.
- Authenticate to Cosmos DB exclusively using token-based authentication via the pre-assigned User-Assigned Managed Identity, instantiated using `DefaultAzureCredential` configured with the specific `ManagedIdentityClientId`. Absolutely zero connection strings, master keys, or account keys are permitted in code, configurations, or logs.
- Utilize `Microsoft.Azure.Cosmos` and `Azure.Identity` packages for
  secure, token-based database interactions, including data-plane CRUD operations like adding and deleting items.
- Include `Azure.ResourceManager` and `Azure.ResourceManager.CosmosDB` packages to programmatically provision the Cosmos DB database and container via the control plane inside the application startup lifecycle (`Program.cs`) before the web application runs, utilizing the same token-based Managed Identity credentials for authentication.
  - ARM provisioning is best-effort; Managed Identity RBAC for ARM may differ from data-plane RBAC.
  - CRUD (and data-plane creation if needed) must be done via the Cosmos SDK (data-plane) using token-based Managed Identity credentials; access keys must not be used.
  - After ARM attempt, startup must run token-authenticated data-plane `CreateDatabaseIfNotExistsAsync` and `CreateContainerIfNotExistsAsync` and only proceed if the database/container are available (either already exist or were created). If token-authenticated data-plane create-if-not-exists fails, startup must fail.
- Map and bind all configuration values, including `AZURE_MANAGED_IDENTITY_CLIENT_ID`, endpoint URLs, and resource names, directly from the environment variables **using the exact keys** defined in `docs\CONTAINER_ENVIRONMENT_VARIABLES.md` without using local settings configuration files as fallbacks.

**Current Context:** Implementation should be centered in `src/backend/Program.cs`, `src/backend/OuterloopLabApi.sln`, the backend web API project already added to that solution (assumption if the project scaffold is missing: `src/backend/OuterloopLabApi/OuterloopLabApi.csproj`), `src/frontend/index.html`, and the React application entry/UI files `src/frontend/src/App.tsx` and `src/frontend/src/main.tsx` (assumption: standard Vite TypeScript layout if those files do not yet exist). The backend must own rate lookup, provider-response normalization, audit-record creation, and Cosmos persistence; the frontend should only collect user input, call the backend API, and render the current conversion plus recent audit history.

**In Scope:**
- Add a backend HTTP endpoint in `src/backend` that accepts a single currency conversion request (`amount`, `fromCurrency`, `toCurrency`), fetches the current rate from the configured external provider, computes the converted amount, and returns a normalized response.
- Persist one immutable audit record per successful conversion in Cosmos DB, including request values, normalized rate data, provider date/marker, backend execution timestamp, and the computed converted amount.
- Add backend read endpoints for audit reconstruction: fetch a conversion by audit id and list recent conversions in reverse chronological order.
- Add a frontend flow in `src/frontend` that lets the analyst enter amount/source currency/target currency, submit the conversion, view the returned result immediately, and view recent prior conversions without leaving the app.
- Surface provider or mapping failures as stable domain-level API errors the frontend can render clearly to the analyst.

**Out of Scope:**
- Bulk or scheduled currency conversions.
- User authentication, authorization, or auditor-specific access control changes.
- CSV/PDF export, email delivery, or external compliance reporting workflows.
- Historical backfill of pre-existing conversions from spreadsheets, email, or third-party portals.
- Support for manually overriding provider rates or editing/deleting stored audit records after creation.

**Feature Constraints:**
- Use `IHttpClientFactory` for outbound currency-rate HTTP calls so provider access is isolated behind a dedicated service and can be validated independently.
- Normalize third-party provider responses into an internal rate model before business logic or persistence; controllers and Cosmos entities must depend on the normalized model, not raw provider JSON.
- Use `decimal` for all monetary values and rates; reject zero or negative amounts and require three-letter uppercase ISO-style currency codes before calling the provider.
- Create the audit record only after a successful normalized rate lookup and include a deterministic record id plus all request/response fields needed to reconstruct the calculation without recalculating later.
- Return RFC 7807 `ProblemDetails` for validation errors and upstream-provider unavailability; do not leak raw exception messages, stack traces, or serializer details to API callers.
- Keep conversion math on the backend only; the frontend must display server-returned amounts rather than recomputing values locally.
- Show recent audit records newest-first in the UI and prevent duplicate submissions during an in-flight conversion request.

**Expected Outcome:** When an analyst submits `amount=100.00`, `fromCurrency=USD`, and `toCurrency=EUR`, the backend returns a normalized payload containing an audit id plus fields equivalent to `amount: 100.00`, `fromCurrency: "USD"`, `toCurrency: "EUR"`, `rate: 0.92`, `convertedAmount: 92.00`, `providerDateOrMarker: "2026-08-01"`, and `executedAtUtc: "2026-08-01T14:23:45.123Z"` (timestamp value will vary, but it must include sub-second precision generated by the backend). The exact same values are persisted as one immutable Cosmos audit record and can be retrieved later by id and from a recent-history endpoint ordered newest-first. If the external provider is unavailable or returns a payload that cannot be mapped into the internal model, the API responds with HTTP 503 and an RFC 7807 `ProblemDetails` body carrying a stable domain message such as `Currency rate provider unavailable`; the frontend renders that message without exposing raw network/serialization exception text.
